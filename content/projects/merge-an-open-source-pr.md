## Overview

This is the one project on the list with no starter code, because the "build" is a real contribution to a real open-source project: find a genuine issue, understand an existing unfamiliar codebase well enough to fix it, open a pull request, and get it through review to merged. There's no scaffolding to follow and no spec handed to you — the whole exercise is doing what every working developer does constantly and almost no course teaches directly.

## Why it's worth building

Reading and modifying a large, unfamiliar codebase you didn't write is a completely different skill from building your own project from scratch, and it's the one you'll use every single day on a real team. This project also puts you through the parts that are genuinely uncomfortable the first time — asking a maintainer a clarifying question, receiving review feedback on code you thought was done, waiting on a response — in a low-stakes setting where the worst outcome is a closed PR, not a missed deadline. Doing it once removes most of the anxiety around doing it as your job.

## Build this

- Find a project you already use or find interesting, and identify a real, appropriately-scoped issue (a labeled "good first issue" is a reasonable place to start, but isn't required)
- Get the project running locally, including its test suite, before writing any code
- Read enough of the surrounding code to match its existing patterns and conventions, not just your own preferred style
- Make the change, add or update tests per the project's own conventions, and write a clear PR description explaining the what and why
- Respond to review feedback and push follow-up commits until it's merged (or, if it's rejected, document what you learned from the maintainer's reasoning)

## The constraint that makes it real

You don't control the codebase, the conventions, or the reviewer's schedule — the constraint is working inside someone else's system exactly as it exists, not the version you'd have built yourself. That means matching existing code style even when you'd write it differently, understanding why a seemingly odd pattern exists before "fixing" it, and treating review feedback as information rather than a personal judgment. A PR that gets merged after two rounds of feedback is a better outcome, and a more honest signal of real-world readiness, than one that happened to be perfect on the first try.

## What you'll practice

- Reading and navigating an unfamiliar, real-world codebase
- Matching existing conventions instead of imposing your own
- Writing a clear PR description and responding professionally to code review
- Working within a project's existing test and contribution process
- The actual, unglamorous mechanics of contributing to software you don't own
